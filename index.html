Transactional Systems

CPOS — Transaction Integrity in Live Retail Operations

LancolaTech · Point-of-sale platform · Live production use, Eldoret

Context

CPOS is a point-of-sale system used by retail businesses to process real transactions — sales, terminal actions, and stored records all had to agree with each other, in production, under real staff usage rather than test conditions.

Engineering Challenge

A terminal action (a sale, a void, a correction) had to be reflected in the backend's transaction record exactly once — never duplicated, never dropped — even when a network interruption, a retry, or a terminal restart occurred mid-operation.

What I Built

Backend transaction handling and API endpoints that recorded terminal actions against a relational database, with logic to detect and prevent duplicate or partial writes when a request was retried or interrupted before confirmation.

Technical Decisions

  • Used PostgreSQL for its transactional guarantees — an interrupted operation needed to either fully commit or fully roll back, with no partial state in between.
  • Kept terminal-facing logic simple and pushed consistency enforcement to the backend, so a slow or unreliable terminal connection couldn't leave the system in an ambiguous state.
  • Traded some implementation simplicity for explicit idempotency checks on write operations — more code up front, fewer reconciliation problems in production.

Reliability Considerations

  • Network drop mid-transaction: a terminal could show a sale as "processing" with no confirmed backend record — handled by having the backend treat unconfirmed writes as retryable rather than final.
  • Duplicate submission from a retried request: guarded against re-recording the same sale twice.
  • Not every edge case around concurrent terminal access was fully hardened at every stage of the project — ongoing work as usage patterns surfaced new scenarios.

Outcome

The system is in active use by retail businesses in Eldoret, processing real transactions as part of daily operations.

Lessons Learned

Working on CPOS shaped how I think about any system where a record has to be trusted after the fact — the discipline of preventing ambiguous state applies well beyond retail, to any environment where an interrupted operation can't be allowed to leave an unclear result.

Distributed State

E-commerce State Synchronization — Frontend/Backend Consistency Under Failure

E-commerce shopping cart · Frontend/backend consistency

Context

A shopping cart's displayed state (what the user sees) and its backend state (what's actually stored) have to match. Real user behavior — fast repeated clicks, multiple tabs, slow network responses — creates opportunities for the two to drift apart.

Engineering Challenge

Cart actions (add, remove, change quantity) sent to the backend in quick succession could arrive and be processed out of order, so the last action a user took wasn't necessarily the last one applied to the stored cart.

What I Built

Debugged and reworked the interaction between frontend cart actions and backend state updates so that the order actions were applied matched the order the user actually performed them in, even under rapid or overlapping requests.

Before / After: Request Ordering

Technical Decisions

  • Investigated whether the fix belonged on the frontend (sequencing requests before they're sent) or backend (resolving order on arrival) — chose to address ordering at the point where requests were dispatched, since that's where the true user-intended order was known.
  • Weighed a full optimistic-UI rework against a smaller, targeted fix to the request sequencing — chose the targeted fix to avoid introducing new failure modes in an already-working UI.

Reliability Considerations

  • Rapid repeated clicks (add, then quickly remove) could reach the backend in reverse order — this was the core failure mode investigated and addressed.
  • Verified the fix under repeated manual testing with fast, overlapping input rather than relying on a single pass-through test.
  • Multi-tab usage (same cart open in two tabs) was identified as a related but distinct problem, out of scope for this specific fix.

Outcome

The cart's displayed state matched backend-stored state under the rapid-input conditions that previously caused drift.

Lessons Learned

This project sharpened how I think about state ownership — deciding which side of a system is responsible for resolving order or truth, rather than letting both sides guess independently.

Backend Fundamentals

FastAPI Task Management API

Independent project · CRUD, routing, validation, error handling

Context

A task management API needs a backend that can reliably create, read, update, and delete tasks while validating input and returning clear errors — the basic contract any client depends on.

Engineering Challenge

Before adding any complexity — a database, AI integration, orchestration — the fundamentals had to be solid: routing, HTTP methods, validation, and application state, each done deliberately rather than assumed.

What I Built

A FastAPI application exposing REST endpoints for task creation, retrieval, updates, and deletion, using in-memory storage first to isolate backend logic before introducing database persistence.

Technical Decisions

  • Used Pydantic models for request/response validation, so malformed input is rejected before it reaches business logic.
  • Sequenced complexity deliberately — in-memory storage first, database persistence later — to isolate and understand each layer on its own.

Reliability Considerations

  • Explicit error responses (404 for missing tasks, 422 for validation failures) rather than generic failure messages.
  • Validation handled at the schema level, so invalid state can't enter the system through a malformed request.

Outcome

Quantitative results (response times, request-handling benchmarks) to be added once measured.

Lessons Learned

Getting validation and error handling right at the smallest scale made it clear how much of "backend reliability" is decided before scale ever becomes the problem.

AI + Backend

AI-Powered Backend Application

Independent project · API integration, data workflows

Context

An AI-powered feature is only as reliable as the backend feeding it and handling its output — the surrounding system has to be engineered as carefully as the AI call itself.

Engineering Challenge

A slow response, a malformed output, or a failed AI call shouldn't break the application for the user — that failure handling had to be designed explicitly, not assumed away.

What I Built

A backend service that prepares and sends a request to an AI API, handles the response including failure and timeout cases, and returns a structured result to the client regardless of what happened underneath.

Technical Decisions

  • Kept the AI-integrated workflow in a dedicated endpoint, separate from the application's core logic, so a failure there doesn't cascade elsewhere.
  • Returned a consistent, validated response shape to the client whether the AI call succeeded or failed gracefully.

Reliability Considerations

  • Explicit handling for AI-call failure modes — timeouts, malformed responses, rate limits — rather than letting them surface as unhandled errors.
  • Not every possible AI-provider failure mode has been exercised in production; this is an area for continued hardening.

Outcome

Quantitative results (response times, failure-handling rates) to be added once measured.

Lessons Learned

Most of the real engineering work in an "AI-powered" feature is in the backend around the AI call — the same fundamentals from the task management API turned out to matter just as much here.

Cloud-Native

Kubernetes / Cloud-Native Deployment

Independent project · Containerization, orchestration, deployment

Context

An application that runs correctly in local development doesn't automatically behave the same way once containerized and deployed under an orchestrator — networking, configuration, restarts, and scaling all introduce behavior local development never has to deal with.

Engineering Challenge

Understanding Kubernetes fundamentals meant actually deploying something and seeing how it behaves when a pod restarts or is rescheduled — not just studying the concepts behind the KCNA certification.

What I Built

A containerized application deployed to a Kubernetes cluster, with deployment and service manifests defining how the application runs, restarts, and is reached over the network.

Technical Decisions

  • Packaged the application as a minimal, explicit Docker image rather than relying on implicit environment state.
  • Handled configuration through Kubernetes-native mechanisms rather than hardcoded values, so the same image behaves correctly across environments.

Reliability Considerations

  • Verified how the application behaves on pod restart and rescheduling, rather than assuming it matches local-development behavior.
  • Service networking tested to confirm traffic reaches replacement pods correctly after a restart.

Outcome

Deployment evidence (pod status, uptime) to be added once captured.

Lessons Learned

Deploying under Kubernetes surfaced questions that never come up locally — what happens on restart, how configuration should separate from the image — and those questions mattered more than the orchestration tooling itself.
